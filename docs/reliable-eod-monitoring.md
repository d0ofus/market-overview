# EOD operation evidence and historical recovery

`EOD operating evidence` runs daily at 00:35 UTC, including holidays and weekends, and can be dispatched manually. It shares the `market-eod-writer` concurrency group with ingestion and storage migration. A single admitted control query establishes actual metered EOD activity for that UTC bucket. It is independent of the Worker ingestion canary/disable gate, never requests market prices and requires only the existing Cloudflare D1/analytics credentials.

The `market-eod` environment variable `EOD_RUNNER_MODE` defaults to `shadow`. Set it to `active` only with the verified public Worker binding/read cutover. Changing that variable alone cannot produce retirement credit. The public cutover must also record `eod_rollout_evidence.id='monitoring:public-activation'` with this exact JSON shape:

```json
{"version":1,"activatedAt":"<actual activation ISO timestamp>","codeRevision":"<40-character deployed Git revision>","marketDatabaseId":"<actual public market D1 UUID>"}
```

Do not backdate activation to private target bootstrap or shadow ingestion. The first complete public delivery is the later of activation and the first accepted publication for every required scope. Sessions whose deadlines passed before activation receive no credit. Rollback must disable public EOD reads and return the monitoring workflow mode to `shadow`; preserve the activation record as historical evidence rather than inventing continued public delivery.

The monitor evaluates the latest **three consecutive exchange sessions whose whole-day usage can be finalized**. Both monitoring and retirement validation use the same cutoff: the earlier of the expected exchange session and the UTC date two days ago. This prevents each newly delivered session's unsettled usage from perpetually moving the window. For example, on Thursday UTC the eligible window can be the preceding Friday, Monday and Tuesday; Wednesday's pending usage does not require waiting for a weekend. Missing evidence on one of those finalizable trading dates still blocks retirement rather than selecting older dates. This replaces the earlier ten-session requirement at the user's direction on 11 September 2026.

Every evaluated session must meet its actual-close-plus-two-hours deadline. The monitor uses the exchange calendar, including early closes and daylight-saving changes, and requires all six scopes for every session. It selects the earliest accepted revision per scope rather than the current pointer. A later correction does not overwrite an on-time original delivery, and a completed ingestion run cannot disguise missing page publications. An absent active daily run, absent scope, pre-close acceptance or late first acceptance fails that session. Newer sessions whose deadlines have elapsed appear separately in `newerSessions`: pending usage does not gate retirement, but a known newer delivery failure still prevents approval. Public page reads fetch only cached monitoring records; they never start collection. Cached status becomes stale after 30 hours and cannot authorize retirement.

Full-UTC-day usage is collected only after a complete additional UTC day has elapsed, allowing for analytics delay. The monitor preserves the real sample time and combines settled EOD D1 response counters with conservative high-water marks from account analytics and shared workflow metering. Cloudflare adaptive analytics remain provider-reported estimates, not invented exact billing totals. Pending reservations, absent ledgers, unknown analytics and missing trading-date records remain pending. Retirement requires whole-day evidence only for the UTC dates of its three evaluated trading sessions. Weekend and holiday telemetry continues to be collected and displayed for operations; missing or failed nontrading buckets do not block retirement. Each usage row exposes `requiredForRetirement` to distinguish these purposes. Both EOD limits (2.5 million reads/50,000 writes) and account operating limits (4.5 million reads/90,000 writes) remain unchanged.

Each daily invocation makes at most three historical analytics requests: two recent correction rechecks and one oldest missing recorded bucket within 30 days. This recovers missed observations after outages without a request storm. All D1 work is admitted through the shared budget adapter. A quota failure defers to a later invocation; it does not increase the limit or repeatedly retry. Because whole-day usage is intentionally delayed, three delivered sessions can still show pending eligibility until those trading dates' UTC usage evidence is available. No weekend observation or weekend bucket is a retirement prerequisite. Historical buckets with no ledger are not manufactured as zero; the three evaluated trading dates must establish their own complete evidence.

`eod-retirement-policy.ts` defines the shared count of three, finalization cutoff and policy version `three-trading-sessions-v1`. `collectEodRolloutMonitoring` writes version-2 records to `monitoring:three-trading-sessions-v1`; `readEodRolloutMonitoring` performs one indexed read for readiness/admin. It rejects old record versions, policy versions, required-session counts and records lacking `usageFinalizationCutoff`/`newerSessions`, so earlier caches cannot authorize the new policy. Retirement submissions likewise require version 2 and the exact `policyVersion`. `assertEodRetirement` independently recollects evidence for the same finalizable calendar window and checks it against the submitted proof, actual public activation, exact first publication IDs/timestamps, the cutover approval and CPU/query measurements. Monitoring eligibility does not itself delete data, remove legacy jobs or alter bindings. Three consecutive observed passing trading sessions remain an elapsed operational requirement.

Historical repair retains validated older bars even when a target-session bar is unavailable, and reports that target gap explicitly. Coverage uses the union of retained and newly verified observations. A retry reopens a previously partial cursor and fetches only unresolved windows; restored rows clear old diagnostics. The runner rejects unordered, duplicate, future-extended or target-truncated exchange grids before provider work. It does not infer listing dates from short histories.

Historical breadth publication revalidates frozen membership provenance. Source types must match the universe, source and verification dates cannot lie after the target session, and a previous matching membership is usable for at most five actual exchange sessions. Bundled lists, unrelated source classes, malformed dates and unverifiable legacy inputs remain unavailable. Current membership is never substituted for an older session's missing evidence.
